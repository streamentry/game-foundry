# EG-006 options: complex-script text rendering (2026-11-23)

Status: **decision document, not an implementation.** No code, font, or third-party package was added or downloaded into the repository. Every option below is **unverified** unless a row says otherwise. Web sources were read on 2026-11-23; the fetched pages were not all complete (see "Research limits").

Inputs: [eg-006-text-spike-2026-11-23.md](eg-006-text-spike-2026-11-23.md) (iterations 1 to 3), [LOCALIZATION.md](../../../LOCALIZATION.md), [05-ACCESSIBILITY-AND-LOCALIZATION.md](../05-ACCESSIBILITY-AND-LOCALIZATION.md), and the Game Foundry [AGENTS.md](../../../../../AGENTS.md) market order (U.S. English first, U.K. English follow-up, Japan first localization candidate, Vietnamese a candidate, not a selection).

## 1. Summary

- The three spikes show **no demonstrated correct shaping or bidi** for Arabic, Persian, Hebrew or Bengali in any column. The uGUI and UI Toolkit Advanced/Standard columns look identical on iOS.
- Some of the failure may be configuration, but **nothing in public sources confirms that ATG was active** in the spike build. A cheap runtime probe (Option A) decides this. The probe is the first step, not a migration.
- Unity's own 6.0 announcement says ATG was "not yet at full parity" and that Urdu, Sindhi, Punjabi and Indian languages had **not been fully tested**. The Unity staff comment on that thread says the RTL support does not extend to uGUI or TextMesh Pro. These are the strongest public reasons to expect the spike result.
- Pre-shaping libraries exist (RTLTMPro, UniText, HQText, Asset Store packages). Each is either uGUI/TMP-only, Arabic-only, unverified on IL2CPP, or carries an Asset Store EULA. None is proven for Mosselora's scripts.
- **Recommendation:** keep complex-script locales off the shipping allowlist (already policy), spend the next cycle on the Japanese and Vietnamese checks that match the market order, and run the ATG runtime probe in the same device session. Do not start a text-stack migration or add a library before that probe.

## 3. Hypothesis checks

### 3.1 Is the failure a configuration issue?

Possible, not proven.

- Unity 6.3 docs (as summarized in search, fetched page returned 404 for the direct URL) state ATG is **not enabled by default** and needs the project setting or per-element `unityTextGenerator`. The spike used both, plus a reflection-based editor script (`AtgProjectSetting.cs`), so the setting may be applied, but this was not checked at runtime.
- Unity's 6.0 announcement said ATG was opt-in, "not yet at full parity" with the old backend, and that **Urdu, Sindhi, Punjabi and Indian languages had not been fully tested** ([Unity forum, 28 Oct 2024](https://discussions.unity.com/t/announcing-full-rtl-language-support/1544214)). This means Indic failures are plausible without any misconfiguration.
- Unity bug history shows ATG-specific problems that were fixed in point releases: Arabic not drawn in Game View (fixed 6000.0.18f1), RTL delete out-of-range (fixed 6000.2.7f1 and 6000.0.59f1). The Arabic Game View issue page itself was unreadable in this session, so the summary is from a search snippet.
- The spike's Standard and Advanced columns being identical is consistent with **either** ATG not engaging **or** ATG and the standard path sharing the same reordering. The spike cannot distinguish them.
- Font-asset requirement: Unity requires dynamic font assets for ATG. The spike used `FontAsset.CreateFontAsset(..., AtlasPopulationMode.Dynamic, ...)`, which matches that requirement. A static font in the chain would throw an error in 6.5+ docs; no such error was logged.

**Cheap probe (Option A), to run on an active macOS session and on iOS Simulator:**
1. Same Arabic, Hebrew and Bengali strings in a UI Toolkit label under Standard and Advanced. Use `TextElement.MeasureTextSize` (or `Label.MeasureTextSize`) to compare widths. Identical widths with ATG on means ATG is probably not engaged or not changing layout.
2. Read back `style.unityTextGenerator` after setting it, and log the project setting value at runtime.
3. Save both PNGs with a fixed Latin control string, so Latin reversal is visible.

Verdict until run: **unknown**.

### 3.2 Can a pre-shaping library fix it?

- **RTLTMPro**: MIT per its GitHub page. Scope is RTL reordering for Arabic, Farsi, Hebrew, with tashkeel support. It is a TMP plugin, so it does not change the uGUI path. Shaping of Arabic joining and Indic scripts is not stated. Unverified.
- **UniText**: MIT, HarfBuzz-based, the closest match to "a real shaper." Its claims are the vendor's own and the repo is a fork of one upstream. Would need an IL2CPP iOS and Android build test. Unverified.
- **HQText** (Chocolate Dinosaur, GitHub): covers Arabic, Persian, Hebrew, Urdu, FreeType default; license and HarfBuzz use not confirmed. Unverified.
- **HarfBuzz itself**: the project's COPYING file was not fetched; check it before any use. Using it directly means writing a native plugin (estimate: 4 to 8 weeks plus testing, assumption).
- **Asset Store packages**: EULA-bound, Arabic-only, contradictory reviews. Not recommended without a probe.

None of these has been run in Mosselora. They are candidates for a bounded spike, not solutions.

### 3.3 Does TextMesh Pro shape Arabic or Indic in 6000.3?

No public evidence that it does. Unity's RTL announcement says RTL support does not extend to TextMesh Pro (Unity staff, [forum](https://discussions.unity.com/t/announcing-full-rtl-language-support/1544214)). Arabic in TMP is handled by third-party plugins in forum practice. An Indic display bug in TMP and legacy text is listed as open in the tracker's search snippets (UUM-130673, "under consideration for 6000.5.X"); the tracker page itself was not readable. **Verdict: not a fix for the failing scripts.**

### 3.4 Native platform rendering

- Feasible on paper. CoreText handles bidi and shaping for Apple text (WWDC22 session 10107, referenced in search results). Android's TextView/Layout uses the OS shaper. Neither is tested for Mosselora.
- Accessibility: native labels can carry VoiceOver and TalkBack semantics, but they live outside Unity's accessibility tree. Unity 6.3 added native screen-reader support, including TalkBack and VoiceOver, via an Assistive Support API, and its 6.4 docs say the app must build and update the hierarchy itself ([Unity 6.3 accessibility docs](https://docs.unity3d.com/Manual/accessibility.html), [6.3 module intro](https://docs.unity.com/en-us/engine/6000.3/manual/accessibility/module-intro.md) via search; not fetched directly). Focus must be synchronized manually (Unity staff comment in search results).
- Cost is the largest of all options, and the spike cannot test it without building the overlay.

### 3.5 Japanese and Vietnamese (the near-term market)

- **Not in the spike.** The spike covered seven scripts; Japanese, Simplified and Traditional Chinese, Korean, and Vietnamese were not tested.
- **Japanese** (Japan is the first localization candidate per AGENTS.md): Japanese is horizontal and does not need Arabic-style joining, so the spike's failures do not directly predict it. The real risks are glyph coverage (kanji and kana), font size, line breaking and kinsoku rules, and fallback behavior on iOS. Unity forum threads report fallback-font problems on iOS 18+ for dynamic OS fonts (user reports, unverified). Noto Sans JP is OFL-1.1 and a variable font ([Fontsource](https://fontsource.org/fonts/noto-sans-jp/about), [search results](https://fonts.google.com/noto?hl=pt)). Its file size was **not measured**; a subset is probably required.
- **Vietnamese** (candidate, AGENTS.md): Latin with diacritics. Precomposed characters should work in legacy and TMP text with a font that covers Vietnamese; combining marks and line-height clipping are the risks. **Unverified.**
- **Chinese and Korean** are on the 30-locale list but not in the AGENTS.md first-market order.

## 4. Product option: defer complex scripts

This is the cheapest option and is already the shipping policy. The market order (U.S. English, U.K. English, Japan, then Vietnamese as a candidate) does not require Arabic, Hebrew, Persian, Urdu, Bengali, Tamil, Telugu, Thai or Hindi in the next release. **Verdict: defer is compatible with the current plan**, but it does not decide whether those locales will ever ship. Evidence that players in those markets want the game is absent (AGENTS.md says market demand is not established for any locale).

## 5. Recommendation sequence

1. **Now, no code:** keep ar, fa, he, ur, hi, bn, ta, te and th off the shipping allowlist (existing policy). Do not start a UI Toolkit migration, a TMP migration, or a library adoption on the current evidence.
2. **Next active session (about 1 to 3 days):** run the ATG runtime probe (Option A) on macOS and iOS Simulator. Record widths, read-back values and screenshots under `docs/qa/`. Outcome decides step 3.
3. **Same session or the following one (about 1 week):** Japanese and Vietnamese probe on iOS Simulator and one physical iPhone, using a bundled OFL font subset. Test kana and kanji, full-width punctuation, line breaking in choice cards, a Latin-plus-diacritics Vietnamese set, and text scale. Native review is required before any claim.
4. **Only if the probe shows ATG engages and changes output for Arabic or Hebrew:** a bounded spike comparing RTLTMPro, UniText and (if needed) native overlay on a fixed set of 10 Arabic, Persian, Hebrew and Bengali strings. License each candidate from its LICENSE file before any import. Test IL2CPP iOS and Android builds.
5. **Only if an RTL locale becomes a commercial priority after U.S., U.K. and Japan:** choose between a licensed shaper (step 4) and native overlays (Option G) based on the spike, and budget the 4 to 7 week migration in the spike doc plus accessibility work.

**Stop criteria:** if the ATG probe shows no change in output on either platform, close the ATG path for this Unity version and record it as a Unity issue candidate. Do not proceed to step 4 on the ATG path. If no RTL locale is prioritized, do not run step 4.
