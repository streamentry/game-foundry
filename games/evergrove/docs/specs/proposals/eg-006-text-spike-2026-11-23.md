## 1. Mechanism (Unity 6000.3)

- **Advanced Text Generator (ATG)** is the HarfBuzz/ICU/FreeType text backend for UI Toolkit. It is opt-in in 6.3 and enabled project-wide via Edit > Project Settings > UI Toolkit > *Enable Advanced Text Generator*. Per-element, use `style.unityTextGenerator = new StyleEnum<TextGeneratorType>(TextGeneratorType.Advanced)` (USS: `-unity-text-generator: advanced`). The spike sets it per element and on the root, so it does not depend on the project checkbox.
  - https://docs.unity.com/en-us/engine/6000.3/manual/uitoolkits/uielements/uie-work-with-text/uie-advanced-text-generator/enable-and-use-atg
  - https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/textgeneratortype/advanced
- **Limitations** (Unity docs): ATG supports dynamic font assets only; static font assets are not supported; glyph-metric customization is unavailable.
- **Direction**: `VisualElement.languageDirection` (`LanguageDirection.RTL`). Unity states RTL alone gives only basic reversal; line breaking and shaping require ATG enabled.
  - https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/uielements/visualelement/languagedirection
- **uGUI cannot use ATG in 6.3.** Unity's 6.5 announcement says ATG becomes the default for UI Toolkit and that uGUI would get ATG only as an opt-in targeted at 6.8, possibly backported later. Current `Text` (uGUI) and TextMeshPro are therefore not an ATG path in this editor. The TextMeshPro claim is inferred from the sources reviewed, not separately verified.
  - https://discussions.unity.com/t/advanced-text-generator-atg-now-default-in-6-5/1715871
- **Platforms**: the sources reviewed do not list per-platform exclusions for ATG; iOS and Android support was **not verified** by this spike (only the macOS player was built).

Implication: migrating the player-facing dynamic text means moving those labels from uGUI to UI Toolkit. It cannot be done by flipping a uGUI setting.

## Iteration 4 (RTL library, 2026-11-23)

Scope: Arabic (ar), Hebrew (he) and Persian/Urdu code paths on legacy uGUI `Text`. Persian (fa) and Urdu (ur) use the same code path but were **not captured** in this session. The Unity project is not changed to UI Toolkit. Complex-script locales remain **off the shipping allowlist** (`LocaleShippingPolicy` is English only).

### Approach chosen

uGUI draws text left to right and does no bidi reordering, so the text is prepared as a string before it reaches the label:

1. **Arabic contextual shaping:** own implementation in `Assets/Scripts/Core/ArabicShaper.cs`. It maps 49 letters (Arabic, Persian and Urdu) to Presentation Forms-B and merges lam-alef into ligatures. Each code point was checked against its Unicode name (Python `unicodedata`, 49 of 49 rows).
2. **Bidi reordering (UAX #9):** vendored BidiSharp in `Assets/ThirdParty/BidiSharp/` (see its `SOURCES.md`). The paragraph is forced to RTL only when the line contains Arabic or Hebrew letters. Brackets are mirrored (L4).
3. **Wrapping:** `RtlText.Wrap` wraps logical text with `TextGenerator.GetPreferredWidth` on each candidate visual line, so each visual line is reordered on its own. Explicit newlines start new paragraphs.
4. **Integration:** `CjkLineBreakFixer` (now also RTL-aware) is attached to labels, button captions and the save warning in ar, fa, ur and he. Left-aligned text is mirrored to right alignment for those locales; centered text stays centered. The logical source is kept and re-fitted on resize.

## Iteration 5 (Bengali visual order, 2026-11-24)

**Mechanism.** uGUI draws code points left to right with no Indic shaping, so a Bengali pre-base vowel sign is drawn after its consonant. `Assets/Scripts/Core/IndicVisualOrder.cs` (pure C#, no third-party code) pre-orders `bn` text per line:

- Pre-base signs ি (U+09BF), ে (U+09C7) and ৈ (U+09C8) move before the syllable cluster they attach to, including virama-joined conjuncts and a trailing nukta.
- Two-part vowels are split first: ো (U+09CB) becomes ে + া (U+09BE), and ৌ (U+09CC) becomes ে + ৗ (U+09D7). Only the pre-base part moves.
- Latin, digits, punctuation and line breaks are unchanged. A sign with no consonant before it keeps its position. Any exception falls back to the input.
- Hooked into the locale-gated text paths in `EvergroveApp.cs`: `Label`, button captions and the save-warning caption. Other locales never call it.

References: Unicode Bengali block U+0980 to U+09FF (https://www.unicode.org/charts/PDF/U0980.pdf); Microsoft OpenType Bengali shaping notes (https://learn.microsoft.com/typography/script-development/bengali).

**Limits.** No conjunct ligatures (for example ক্ষ), no reph and no below-base forms. uGUI cannot form these. Native review is required.

**Verification.**
- C# tests: `Evergrove C# tests passed: 39900 assertions`, including the Bengali cases (হলো to হেলা visual order, pre-base before consonant, ে/ৈ, virama clusters, Latin and digits untouched, multi-line and CRLF, other locales untouched) and a no-throw pass over every entry of `bn.json` that checks character counts.
- `tools/verify_evergrove_project.py` and `tools/check_evergrove_docs.py`: pass.
- iOS Simulator (Mosselora QA iPhone, iOS 26.5, IL2CPP Debug): Unity build and xcodebuild succeeded on the merged tree. Tour captures 01, 04 and 10 with `bn` set (`AppleLanguages` bn, `AppleLocale` bn_BD) are in `docs/qa/ios-simulator-2026-11-23/locales/bn/`. No dotted circles appeared, and the vowel signs sat in the expected positions in the captures reviewed. The app log for the tour showed no exception.
- Development Console: no exception appeared in the overlay or the app log.

**Verdict.** Partial. The pre-base ordering works for the common cases in the captured strings. Conjunct and reph forms are not handled. Bengali stays off the shipping allowlist until a native reader reviews the captures.

- Visual result: formed conjuncts with no visible hasanta in "সিদ্ধান্ত", "জন্য", "স্মৃতি" and "প্রাণবন্ত". **Verdict: pass, visual only.** Non-native reader; native review is required.
- **Confound:** row 4 uses the system Bengali cascade font, while rows 1 to 3 use Noto Sans Bengali. The result therefore shows CoreText shaping with the system font. It does not isolate the shaper from the font. A follow-up would render Noto through CoreText (font loaded from a file, which is a separate decision).
- Accessibility: a bitmap is invisible to VoiceOver. The accessible label has to be carried separately (for example as a semantic node that holds the string, like the existing `ScreenReaderBridge` pattern). That was not read or tested in this spike.
- Binary size: the plugin links only system frameworks (CoreText, CoreGraphics). The plugin code is a few kilobytes. Not measured against a baseline build.
- Android: not built. The equivalent path would be Android `StaticLayout` or `Canvas` text drawn into a bitmap. Not tested.
- Clean-up: the build touched `ProjectSettings/ProjectSettings.asset`, which was restored. `UIToolkitProjectSettings.asset` (ATG on) is kept on this branch only. The Noto fonts under `Assets/Resources/Dev/Noto` add about 2.5 MiB to every build. They must not be merged as they are.

**Verdict.** ATG (project setting plus per-element) is **not shown to shape** Bengali conjuncts on iOS in Unity 6000.3. Native CoreText **does** form them visually. The native path is viable on iOS, but it is a bitmap, so accessibility has to be designed in.

**Recommendation (effort ranges are assumptions, not measured):**
1. Do not migrate the uGUI UI to UI Toolkit on the strength of ATG. That path has failed for Bengali in three iterations.
2. If bn ships, use a native text overlay for bn on iOS (plugin, bitmap, and a semantic label). Estimate 1 to 2 weeks for iOS, including accessibility mapping. Add an equivalent Android `StaticLayout` path for 1 to 2 weeks, plus device testing.
3. Otherwise ship bn later. The current allowlist keeps bn off the release set, which is the cheapest option.
4. Native-speaker review of the captured conjuncts is required before any claim. Rerun with Noto through CoreText to separate the font effect from the shaper effect.
